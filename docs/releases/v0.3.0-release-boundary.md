# v0.3.0 Release Boundary, Authority Journeys, Non-Goals, and v0.4.0 Dependency Map

## 1. Governance Reference and Authority Baseline

This document specifies the authoritative operational boundary, architectural journeys, capability matrix, explicit non-goals, and v0.4.0 dependency mapping for **Milestone v0.3.0 — Organization Identity and Portal Alpha** within `OSHEThai/oshe-platform`.

- **Governing GitHub Issue:** [OSHEThai/oshe-platform Issue #74](https://github.com/OSHEThai/oshe-platform/issues/74) (`[V030-I001] Draft the v0.3.0 Release Boundary, Authority Journeys, Non-Goals, and v0.4.0 Dependency Map`) under Topic `V030-T00`.
- **Governing Human Decision:** **`HDEC-V030-ENTRY-AND-POLICY-052`** (*v0.3.0 Entry, Organization Authority, Privacy, and Portal Policy Baseline*), approved by the Sole Human Owner on 2026-09-05.
- **Architectural Reference Baseline:** `docs/qualification/v0.3.0-owner-decision-baseline.md`.
- **Release Classification:** `INTERNAL_ENGINEERING_ALPHA`.
- **Operating Environment:** Single-node local development container profile (`deploy/local/compose.dev.yaml`) operating strictly on synthetic or redacted engineering fixtures (`V020-D05`).

### 1.1 Strict Non-Recommendation, Non-Approval, and Non-Acceptance Attestation
In strict conformance with project governance rules and lease `LEASE-V030-I001-RELEASE-BOUNDARY-001`:
1. **No Release Recommendation:** This document articulates the structural boundary and authority scope of Milestone v0.3.0. It conveys **zero recommendation for milestone release, public deployment, or operational rollout**.
2. **No Release Approval:** Operational release, package publication, and deployment authority remain the exclusive, non-delegable authority of the Sole Human Owner.
3. **Zero Residual-Risk Acceptance:** The AI agent role **does not accept, waive, or sign off on any residual risk**. All residual risks remain reserved for human determination under deferred gates `H030-007` and `H030-008`.
4. **Provisional Scope Invariant:** All specifications herein define in-memory and local container capabilities only. Live production infrastructure, commercial cloud provider integrations, and public internet access remain unobserved, unconfigured, and unexecuted.

## 2. Approved Milestone Scope and Explicit Non-Goals

### 2.1 Approved Capabilities (v0.3.0 Scope)
In accordance with decisions `H030-001` through `H030-006` in `HDEC-V030-ENTRY-AND-POLICY-052`, Milestone v0.3.0 delivers the following capabilities:

1. **Six-Level Organizational Hierarchy (`H030-002`):**
   - Canonical six-level hierarchy structure: `Tenant` $\rightarrow$ `Company` $\rightarrow$ `Business Unit` $\rightarrow$ `Project` $\rightarrow$ `Site` $\rightarrow$ `Area`.
   - Strict parent consistency and validation rules; archived parent states block child attachment.
2. **Sponsored Party and Contractor Modeling (`H030-002`):**
   - Third-party contractors and subcontractors modeled strictly as sponsored, bounded participation relationships.
   - Preservation of complete historical attribution; irreversible data deletion is strictly prohibited.
3. **Default-Deny Scoped Authorization & Explicit Delegation (`H030-003`):**
   - Default-deny evaluation across all actions and resources.
   - Fine-grained scoping by project and site; conflict detection and source-authority validation.
   - Prohibition of implicit delegation; all delegated privileges must be explicit and strictly time-bounded.
4. **Local Identity and User Lifecycle Baseline (`H030-004`):**
   - In-memory local synthetic identity management with high-entropy token hashing (SHA-256).
   - External user identities require explicit organizational sponsorship, bounded validity, and manual renewal.
5. **Data Minimization and Exact-Scope Directory Visibility (`H030-005`):**
   - Strict directory access filtering; discovery across unrelated projects or companies is prohibited.
   - Synthetic or redacted engineering data exclusivity; live customer data and real PII are strictly barred.
6. **Snapshot-Only Portal Publication Architecture (`H030-006`):**
   - Static, approval-governed snapshot generation and publication for customer/public portals.
   - Complete decoupling from internal transactional database tables and private API routes.
   - Public fixtures remain non-indexed by search engines (`noindex, nofollow`).

---

### 2.2 Explicit Non-Goals (Strictly Excluded from v0.3.0)
The following capabilities are explicitly outside the scope of Milestone v0.3.0 and are prohibited from being implemented, claimed, or activated in this milestone:

- **NG-01: External Identity Provider Activation:** No integration with external OAuth2, OIDC, SAML 2.0, Microsoft Entra ID, or Okta services (`H030-004`).
- **NG-02: External Public Route and CDN Exposure:** No public internet domain registration, DNS configuration, CDN edge caching, or public route activation (`H030-007 HOLD`).
- **NG-03: Live Portal Queries:** No direct, real-time database querying from the portal layer to operational transactional schemas (`H030-006`).
- **NG-04: Real Customer and Production PII Data:** No processing or ingestion of actual customer data, worker personal records, government IDs, or medical data (`H030-005`).
- **NG-05: Mobile Edge Synchronization Daemon:** No background delta synchronization daemon, mobile SQLite offline synchronization, or peer-to-peer mesh transport (deferred to v0.4.0).
- **NG-06: Production Deployment and Release Signing:** No production packaging, deployment to public cloud hosts, artifact signing, or milestone release approval (`H030-008 HOLD`).
- **NG-07: Advanced Cross-Tenant Analytics:** No cross-tenant benchmark aggregation, machine learning inference, or automated safety risk scoring.
- **NG-08: Irreversible Data Deletion:** No hard deletion of organizational entities, users, or audit journals (`H030-002`).

## 3. End-to-End Authority Journeys

Milestone v0.3.0 defines seven canonical end-to-end authority journeys that govern execution across the kernel modules:

```
====================================================================================================
v0.3.0 AUTHORITY JOURNEY LIFECYCLE
====================================================================================================

[ Journey 1: Hierarchy & Party Setup ]
  Tenant -> Company -> Business Unit -> Project -> Site -> Area
  └── Sponsor Contractor / Subcontractor (Bounded Association)
             │
             ▼
[ Journey 2: Scoped Authorization & Delegation ]
  Default-Deny Policy -> Role Assignment -> Scope Narrowing -> Time-Bounded Delegation
             │
             ▼
[ Journey 3: Synthetic User Lifecycle ]
  Internal Synthetic User / Sponsored External User -> Token Issuance -> Active Session
             │
             ▼
[ Journey 4: Directory Visibility & Minimization ]
  Caller Token Context -> Exact-Scope Filtering -> Anti-Enumeration & Redaction
             │
             ▼
[ Journey 5: Portal Snapshot Generation ]
  Authoritative Data Aggregation -> Format Transformation -> Immutable Snapshot Staging
             │
             ▼
[ Journey 6: Publication Governance & Presentation ]
  Approval Review Gate -> Snapshot Publication -> Non-Indexed Presentation (TB-07)
             │
             ▼
[ Journey 7: Historical Attribution & Audit ]
  Append-Only Audit Recording -> Attribution Retention -> Zero Hard Deletion
====================================================================================================
```

### 3.1 Journey 1: Organization Hierarchy and Sponsored Party Onboarding
1. **Tenant Provisioning:** Initial tenant context established with canonical identifier (`ten_*`).
2. **Hierarchy Construction:** Authoritative tree instantiated sequentially: Company (`cmp_*`) $\rightarrow$ Business Unit (`bnu_*`) $\rightarrow$ Project (`prj_*`) $\rightarrow$ Site (`ste_*`) $\rightarrow$ Area (`ara_*`). Each child explicitly binds to its active parent.
3. **Contractor Sponsorship:** Primary organization sponsors an external contractor entity (`prt_*`). The association defines bounded operational scope (specific project and site), valid date range, and supervising party.
4. **Historical Immutability:** Renaming or restructuring preserves historical attribution; archived entities cannot accept new child attachments or operational mutations.

### 3.2 Journey 2: Scoped Authorization and Time-Bounded Delegation
1. **Access Request Submission:** Caller requests action evaluation providing subject identity, target resource, and operational scope.
2. **Default-Deny Evaluation:** Policy evaluator rejects any request lacking an explicit grant (`DenialReasonDefaultDeny`).
3. **Scope Matching:** Validates caller's role is bound to the exact project/site of the target entity. Hierarchy membership alone conveys zero implicit permission escalation.
4. **Delegation Processing:** If access relies on delegation, evaluator verifies:
   - Delegation record is explicit and active.
   - Current timestamp is strictly within the time-bounded window (`valid_from` $\le$ `now` $\le$ `valid_to`).
   - Delegating party possessed the necessary authority at grant time.
5. **Audit Logging:** Every authorization decision (permit or deny) is logged in the append-only journal with non-leaking diagnostic summaries.

### 3.3 Journey 3: Local Synthetic User Lifecycle and External User Sponsorship
1. **User Instantiation:** User entity created with canonical user identifier (`usr_*`) and role assignments in `MOD-IAM`.
2. **External User Sponsorship:** If user is an external contractor, an internal sponsor identity (`usr_*`) and explicit expiration timestamp are bound to the profile.
3. **Session Token Issuance:** Server issues high-entropy synthetic bearer token (`oshe_tok_<64-hex>`). Only the SHA-256 token digest is retained in memory; raw credentials are never stored.
4. **Revocation & Renewal:** Sessions can be revoked individually or globally by subject. Sponsored external users must undergo explicit manual renewal prior to expiration; expired users fail closed immediately (`DenialReasonIdentityInactive`).

### 3.4 Journey 4: Privacy-Preserving Exact-Scope Directory Resolution
1. **Directory Query Ingress:** Caller requests user or entity listing within organization.
2. **Context Resolution:** Ingress gateway resolves caller's trusted tenant context and project scope from session claims.
3. **Exact-Scope Filtering:** Query engine filters directory entries strictly matching caller's assigned project and company. Cross-project discovery is strictly denied.
4. **Anti-Enumeration Safeguards:** Directory outputs apply strict pagination boundaries and data minimization, returning only operational names and roles while suppressing personal contact details or sensitive attributes.

### 3.5 Journey 5: Portal Snapshot Generation and Staging
1. **Aggregation Trigger:** An authorized compliance lead initiates portal export generation for an approved inspection report or safety metric.
2. **Source Data Extraction:** Reporting engine queries authoritative PostgreSQL schemas (`mod_wfa`, `mod_rec`, `mod_evd`) within tenant scope.
3. **Transformation to Static Snapshot:** Engine formats data into static, pre-rendered JSON/HTML structures.
4. **Cryptographic Sealing:** Engine computes SHA-256 digest over the aggregated data payload and embeds a mandatory `DERIVED_OUTPUT_NON_AUTHORITY` notice.
5. **Staging:** Snapshot stored in provisional portal staging registry with status `STAGED_PENDING_APPROVAL`.

### 3.6 Journey 6: Portal Publication Governance and Non-Indexed Presentation
1. **Formal Review Gate:** A designated human authority or authorized reviewer inspects the staged snapshot and attached source data digest.
2. **Publication Approval:** Reviewer records explicit approval metadata (approver ID, timestamp). Status transitions to `PUBLISHED_IMMUTABLE`.
3. **Decoupled Presentation:** Portal service serves the published snapshot from local memory/static store. Zero live database connections or API routing to operational transactional tables exist.
4. **Search Engine Shielding:** HTML responses embed `<meta name="robots" content="noindex, nofollow">` headers, ensuring public fixtures remain unindexed and hidden from external web discovery.

### 3.7 Journey 7: Historical Attribution Preservation and Append-Only Audit
1. **Operational Event Generation:** Every lifecycle transition, authorization check, and snapshot publication emits an immutable event envelope (`MOD-EVT`).
2. **Sequential Logging:** Audit journal records entry with monotonic sequence counter, UTC timestamp, actor identity, correlation ID, and prior/new state.
3. **Zero Hard Deletion:** When entities terminate, state transitions to `ARCHIVED`. Underlying records, snapshots, and audit journals are permanently preserved to maintain regulatory non-repudiation.

## 6. Assumption Register and Operating Posture

### 6.1 Baseline Technical Assumptions
1. **Local Container Runtime:** The platform kernel executes within the local single-node development profile (`deploy/local/compose.dev.yaml`) comprising Go 1.26.5, Node 24.20.0, Python 3.14.7, PostgreSQL 17.11, SeaweedFS 4.29, NATS JetStream 2.14.5, Valkey 9.1.1, and Meilisearch 1.51.
2. **Deterministic Time Controls:** Temporal policies (token expiry, delegation windows, freshness bounds) are qualified using deterministic injectable clock interfaces (`Clock`).
3. **Synthetic Engineering Data Baseline:** In accordance with decision `V020-D05`, all fixtures, test seeds, and user accounts utilize synthetic, fictionalized, or redacted low-risk data. Zero customer data or real PII is present.
4. **Fail-Closed Security Posture:** Any parsing failure, missing claim, expired token, mismatched tenant context, or unfulfilled condition aborts execution immediately with a generic, non-leaking denial.
