### 2.2 Qualification Evidence Contract (Required Before Compatibility Claims)
In strict adherence to `V020-D02` and project governance, compatibility or qualification cannot be claimed in advance. When an actual test execution or qualification run is performed under a future execution lease, the following exact evidence fields must be captured and recorded:
1. `host_operating_system`: Exact OS distribution and kernel release.
2. `cpu_architecture`: Hardware processor architecture (e.g., `x86_64`, `arm64`).
3. `container_engine_identity`: Exact Docker Engine and Compose build digests.
4. `service_image_digests`: Immutable SHA-256 digests for every container image in Compose.
5. `toolchain_reproducibility`: Exact toolchain binary versions and lockfile integrity hashes (`pnpm-lock.yaml`, `go.sum`).
6. `browser_engine_version`: Exact headless/desktop browser revision used for client testing.
7. `network_binding_profile`: Exact loopback/container interface bindings and exposed port manifest.
8. `configuration_digest`: SHA-256 hash of the sanitized runtime environment configuration.

*Note: No observed host, performance, or runtime facts are invented in this specification; qualification evidence must derive solely from authorized execution telemetry.*

## 3. Data Classification, Retention, and Migration Limits

### 3.1 Permitted vs. Prohibited Data Classes (`V020-D05`)
All development, testing, and alpha usage are subject to strict data boundaries:

- **Permitted Data Classes**:
  - `SYNTHETIC_DATA`: Programmatically generated test fixtures and mock domain models.
  - `REDACTED_DATA`: Low-risk engineering configuration and non-identifying sample records.
- **Strictly Prohibited Data Classes**:
  - `CUSTOMER_DATA`: Real customer records, user identifying data, or actual inspection observations.
  - `PRODUCTION_DATA`: Clones, snapshots, or fragments of production databases.
  - `PRODUCTION_SECRETS`: Live credentials, API keys, private keys, or signing certificates.
  - `MEDICAL_DATA`: Clinical records, health surveillance data, or worker medical assessments.
  - `SECURITY_CASE_DATA`: Live incident response logs, forensic artifacts, or vulnerability disclosures.
  - `LEGAL_PRIVILEGED`: Privileged communications, litigation files, or formal legal opinions.

### 3.2 Evidence Retention & Integrity Rules
- Original files uploaded to SeaweedFS (S3 API) are immutable (`NFR-V020-EVD-001`).
- Every stored evidence asset requires an immutable SHA-256 content digest recorded in database records before marking acceptance.
- Zero client direct-access keys: all storage reads and uploads are mediated by tenant-scoped presigned URLs with short-lived TTLs.
- Automatic secret scanning (`NFR-V020-SEC-002`) via `tools/validate_repository.py` is enforced across all fixtures, documents, and code.

### 3.3 Migration, Restore, and Recovery Limits (`V020-D08`)
- **Allowed Local Migration Scope**:
  - `M0`: Clean installation on an empty database.
  - `M1`: Forward schema and data migration upgrade.
  - `M2`: Simulated partial failure recovery and non-destructive forward-fix.
- **Tested Restore Prerequisite (`NFR-V020-BKP-001`)**: Backup credibility requires a demonstrated, tested restore procedure under the supported local profile.
- **Destructive Migration Boundary (`M3`)**: Any destructive, irreversible, or data-loss schema migration is strictly prohibited without a separate, explicit Sole Human Owner decision.

## 4. Non-Functional Requirements (NFR) Baselines and Internal Targets

### 4.1 Mandatory Engineering Baselines
The following architectural baselines are non-negotiable prerequisites for the v0.2.0 kernel:

| NFR ID | Attribute | Mandatory Requirement | Release Effect |
|---|---|---|---|
| `NFR-V020-SEC-001` | Tenant Isolation | Default-deny tenant scoping across all module queries and commands; zero cross-tenant query leakage (`V020-D07`). | Release Blocker |
| `NFR-V020-SEC-002` | Secret Exclusion | Complete exclusion of credentials, tokens, and secrets from code, fixtures, logs, and evidence. | Release Blocker |
| `NFR-V020-EVD-001` | Evidence Integrity | Accepted evidence is immutable, SHA-256 verifiable, tenant-scoped, and exportable. | Release Blocker |
| `NFR-V020-AUD-001` | Append-Only Audit | Security and workflow audit events are append-only, capturing actor, context, action, state, time, and correlation. | Release Blocker |
| `NFR-V020-CON-001` | Concurrency Control | Optimistic concurrency control; prohibition of last-write-wins (LWW) on protected records. | Release Blocker |
| `NFR-V020-MOD-001` | Module Encapsulation | Modules own data and internal schemas; direct cross-module private database access is prohibited (`V020-D04`). | Release Blocker |
| `NFR-V020-MIG-001` | Migration Safety | Forward migrations and recovery procedures validated without unrecoverable state (`V020-D08`). | Release Blocker |
| `NFR-V020-BKP-001` | Restore Credibility | Backup validity requires passing end-to-end restore verification. | Release Blocker |
| `NFR-V020-UPL-001` | Upload Reliability | Uploads expose progress/failure, support safe retry, and verify integrity prior to record association. | Required |
| `NFR-V020-L10N-001` | Localization | Locale, time-zone, dates, numbers, and translation fallback explicitly handled (th-TH and en-US). | Required |
| `NFR-V020-OBS-001` | Observability | Failures and denials produce structured, redacted diagnostics without sensitive data. | Required |

### 4.2 Internal Engineering Targets vs. No-Public-Commitment Rule (`V020-D06`)
In strict adherence to `HDEC-V020-GATE-B-APPROVAL-051`, quantitative performance, usability, and restore metrics are approved solely as **internal engineering benchmarks**, not public commitments:

| Metric ID | Parameter | Internal Engineering Target | Limitation & Governance Invariant |
|---|---|---|---|
| `NFR-V020-PERF-001` | Common API Latency | p95 $\le$ 750 ms | Internal benchmark under frozen local alpha load. **Never an external SLA or service guarantee.** |
| `NFR-V020-UX-001` | UI Usability | Usable $\le$ 2.5 s | Target on minimum supported client with assets cached. **Not a public commitment.** |
| `NFR-V020-REC-001` | Environment Restore | $\le$ 8 hours | Internal disaster recovery drill objective following accepted loss decision. |
| `NFR-V020-REC-001` | Transient-State Loss | $\le$ 24 hours | Maximum tolerated recovery point for uncommitted transient state during alpha. |
| `NFR-V020-OFF-002` | Offline Reference Data | Freshness $\le$ 24 hours | Internal cache validity guideline for non-critical inspection templates. |

**Inviolable Quality Invariant:**
No external SLA, uptime percentage, latency guarantee, or scalability claims may be asserted for v0.2.0. The release is explicitly an internal engineering alpha.

## 5. Compatibility Envelope and Default-Deny Exclusions

### 5.1 Supported vs. Unsupported Envelope
- **Supported Environment**: Single-node developer workstation or local build runner executing Docker Compose on modern 64-bit platforms (Windows 11 / Linux x86_64) matching the frozen toolchain.
- **Explicitly Unsupported Environments**:
  - Multi-node Kubernetes or Swarm clustering.
  - Multi-region distributed active-active database configurations.
  - Native mobile application builds (iOS / Android native SDKs).
  - External identity federation (SAML 2.0 / Enterprise OIDC).
  - Production multi-tenant public SaaS hosting.
  - Air-gapped or disconnected physical appliance hardware qualification.

### 5.2 Default-Deny and External Integration Exclusions
- **Tenant Context**: Any operation lacking a valid, verified tenant context is rejected by default (`FAIL_CLOSED`).
- **External AI Providers**: External AI provider routes remain `DENY` / disabled; no external AI service is activated for v0.2.0 kernel execution.
- **Third-Party Services**: External paid APIs, external notification dispatchers (SMS/Email gateways), and third-party analytics are excluded from the kernel baseline.
