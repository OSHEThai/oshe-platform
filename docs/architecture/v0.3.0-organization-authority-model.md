## 2. Module and Data-Ownership Boundaries (No-Direct-Access Rule)

### 2.1 Core Architectural Principles
Under the modular monolith architecture mandated by `ADR-0001` and decision `V020-D04`, the platform kernel is decomposed into nine domain modules. Each module maintains strict, exclusive data authority over its domain entities and relational persistence schemas:

1. **Strict Schema Sovereignty:** Each module owns a dedicated PostgreSQL schema namespace and table prefix. No module may define or manipulate tables within another module's namespace.
2. **Zero Shared Database Tables:** Direct sharing of tables across domain modules is strictly prohibited.
3. **No Direct Cross-Module Writes:** Direct SQL `INSERT`, `UPDATE`, or `DELETE` operations across module schema boundaries are prohibited. All cross-module state transitions must be invoked through public Go contract interfaces or transactional events.
4. **No Private Table Joins:** Cross-module queries must not bypass service boundaries with private SQL joins across schemas.
5. **Transactional Coordination:** Cross-module asynchronous communication is conducted strictly via versioned event envelopes staged through the Transactional Outbox (`MOD-EVT`) in the same ACID transaction as the business entity mutation.

## 3. Tenant, Organization Hierarchy, and Party Trust Boundaries

### 3.1 Six-Level Organization Hierarchy Boundary
In accordance with decision `H030-002`, the platform kernel formalizes a strict six-level organizational tree within tenant boundaries:

```
[ TENANT BOUNDARY (ten_*) ]
  │
  └── [ COMPANY (cmp_*) ]
        │
        └── [ BUSINESS UNIT (bnu_*) ]
              │
              └── [ PROJECT (prj_*) ]
                    │
                    └── [ SITE (ste_*) ]
                          │
                          └── [ AREA (ara_*) ]
```

#### Hierarchy Invariants & Enforcement Rules
1. **Strict Upward Scoping:** Every entity from Company down to Area must explicitly declare and match its parent entity's `TenantID`. Constructing child entities with mismatched or cross-tenant parent references fails closed with `ErrCrossTenantLinkage`.
2. **Deterministic Parent Binding:** A child entity cannot exist without an active, validated parent entity (e.g., an Area requires an active Site; a Site requires an active Project). Attempting to attach children to uninitialized or mismatched parents fails closed with `ErrParentMismatch`.
3. **Archived Parent Freeze:** If a parent entity transitions to `StateArchived`, the entire downstream sub-tree is frozen. Attempting to attach new child contexts or stage new operational records under an archived parent returns `ErrParentArchived`.
4. **Zero Implicit Scope Escalation:** Membership or role assignment at a broader level (e.g., Company) does **not** grant automatic, unconstrained operational permissions at specific sub-scopes (e.g., Project or Site) without an explicit scope grant.

---

### 3.2 Sponsored Party and Contractor Trust Boundary
Under decision `H030-002`, third-party contractors and subcontractors cannot be treated as native internal organization members. They are governed as **sponsored, bounded participation relationships**:

```
+----------------------------------------------------------------------------------------------------+
| TENANT SCOPE (ten_safety_corp)                                                                     |
|                                                                                                    |
|  +-------------------------------------+      SPONSORSHIP BOND       +---------------------------+ |
|  | Sponsoring Internal Organization    |============================>| Sponsored Contractor Party| |
|  | - Supervising Internal Manager      |      (Explicit, Validated,  | - External Company Name   | |
|  | - Internal Sponsor Subject ID       |       Time-Bounded Scope)   | - Bounded Project ID      | |
|  +-------------------------------------+                             | - Bounded Site ID         | |
|                                                                      | - Valid Date Range        | |
|                                                                      +---------------------------+ |
+----------------------------------------------------------------------------------------------------+
```

#### Contractor Governance Invariants
1. **Mandatory Internal Sponsorship:** A contractor party record (`prt_*`) must be explicitly sponsored by an authorized internal organization manager (`usr_*`). Self-onboarding or unsponsored external entity registration is strictly rejected.
2. **Exact Scope Bounding:** The participation relationship must explicitly designate the specific `ProjectID` and `SiteID` within which the contractor is permitted to operate. Access outside this bounded scope is denied by default (`DenialReasonScopeMismatch`).
3. **Temporal Bounding & Expiration:** Every contractor sponsorship record defines strict `ValidFrom` and `ValidTo` timestamps. Upon reaching expiration, access permissions fail closed immediately without requiring manual revocation.
4. **Anti-Enumeration & Isolation:** A contractor cannot enumerate, search, or discover peer contractor entities, unrelated projects, or broader organizational directories (`H030-005`).
5. **Preservation of Attribution (No Hard Deletion):** When contractor contracts terminate or expire, their records and historical actions transition to `StateArchived`. Irreversible database deletions are strictly forbidden to ensure regulatory compliance and legal non-repudiation.

## 4. Interaction Paths Across Kernel Surfaces

Milestone v0.3.0 defines six authoritative interaction paths governing requests across system boundaries:

```
+----------------------------------------------------------------------------------------------------+
| SURFACE INTERACTION ARCHITECTURE                                                                   |
|                                                                                                    |
|   1. DIRECTORY: Caller -> Token Claims -> Exact-Scope Filter -> Sanitized Directory Result         |
|   2. ASSIGNMENT: Manager -> Validate Authority -> Check Role Conflict -> Grant Scoped Role         |
|   3. DELEGATION: Delegator -> Time-Window Check -> Scope Bounds -> Non-Implicit Delegation Record   |
|   4. USER LIFECYCLE: Sponsor -> Synthetic Profile Creation -> Token Issuance -> Bounded Expiry     |
|   5. PORTAL STAGING: Compliance Lead -> Query Engine -> Static Transformation -> Sealed Digest     |
|   6. PORTAL PUBLICATION: Reviewer Approval -> State: Published -> Static Server (noindex, nofollow)|
+----------------------------------------------------------------------------------------------------+
```

### 4.1 Path 1: Privacy-Preserving Directory Resolution (`H030-005`)
- **Objective:** Enable operational contact and role discovery within an authorized project while preventing organizational reconnaissance or cross-tenant data harvesting.
- **Sequence:**
  1. Client submits directory query request providing caller session token.
  2. Ingress gateway extracts bearer token and invokes `IdentityManager.ValidateSession`.
  3. `MOD-ORG` derives immutable `TenantContext` strictly from verified server-side claims; client-supplied tenant headers are stripped.
  4. Query processor filters directory entries strictly matching caller's active `CompanyID` and `ProjectID`. Entries from sibling projects or unrelated companies are excluded at the query boundary.
  5. Response payload enforces data minimization: emits only operational display names, roles, and assigned areas; suppresses personal contact details, government IDs, and internal database keys.

### 4.2 Path 2: Scoped Role Assignment and Conflict Checking (`H030-003`)
- **Objective:** Grant operational permissions to an identity while enforcing segregation of duties and project-level isolation.
- **Sequence:**
  1. Organization administrator submits role assignment command (`AssignRoleRequest`).
  2. Policy evaluator verifies that the assigning party possesses the required administrative entitlement within that specific tenant and scope.
  3. Evaluator executes segregation-of-duties conflict checks (e.g., verifying that a single subject cannot hold both `SafetyInspector` and `ComplianceReviewer` roles on the same inspection workflow).
  4. Role assignment record is created with explicit `ScopeID` (`prj_*` or `ste_*`) and effective timestamp.
  5. Mutation is logged to the append-only audit journal (`MOD-REC`).

### 4.3 Path 3: Time-Bounded Explicit Delegation (`H030-003`)
- **Objective:** Enable temporary delegation of operational authority (e.g., covering supervisor absence) without permanent privilege escalation.
- **Sequence:**
  1. Delegator submits delegation request designating delegate subject ID, specific role, operational scope, `ValidFrom`, and `ValidTo`.
  2. Evaluator validates delegator actively holds the role being delegated and has explicit authority to delegate.
  3. Evaluator verifies time window: `ValidFrom` must be current or future; `ValidTo` must be bounded ($\le$ 30 days maximum alpha ceiling).
  4. Evaluator records an explicit delegation grant in `MOD-IAM`. Implicit delegation (e.g., inheriting permissions by reporting line) is strictly prohibited.
  5. During access evaluation, if caller relies on delegated authority, evaluator verifies monotonic clock is strictly within window; expired delegations fail closed (`DenialReasonDelegationExpired`).

### 4.4 Path 4: Local Synthetic User Lifecycle and External User Sponsorship (`H030-004`)
- **Objective:** Manage internal and external user access using local synthetic credentials while enforcing renewal boundaries.
- **Sequence:**
  1. Internal user created via `MOD-IAM` with canonical identifier (`usr_*`).
  2. If user is external, an authorized internal manager records a sponsorship bond (`SponsorID`, expiration date).
  3. System generates a high-entropy synthetic bearer token (`oshe_tok_<64-hex>`). The token's SHA-256 digest is stored in memory; the raw token is returned once to the caller.
  4. Upon request ingress, `ValidateSession` hashes the incoming token and checks the revocation registry and expiration window.
  5. External users exceeding their validity date are rejected immediately with `DenialReasonIdentityInactive`. Manual sponsor renewal is required to re-establish active status.

### 4.5 Path 5: Portal Snapshot Generation and Cryptographic Sealing (`H030-006`)
- **Objective:** Aggregate operational inspection findings and safety metrics into static, isolated read-model snapshots.
- **Sequence:**
  1. An authorized user triggers snapshot generation for an approved inspection report or safety metric.
  2. Reporting query engine (`MOD-REP`) extracts domain facts from authoritative PostgreSQL schemas within tenant scope.
  3. Engine transforms dynamic data into static JSON/HTML data structures.
  4. Engine computes a SHA-256 digest over the entire data payload (`SourceDataDigest`) and embeds the mandatory `DERIVED_OUTPUT_NON_AUTHORITY` notice.
  5. Snapshot is registered in portal staging store with state `STAGED_PENDING_APPROVAL`.

### 4.6 Path 6: Approval-Governed Portal Publication (`H030-006`)
- **Objective:** Expose customer/public safety reports via decoupled portal views without allowing operational database access or search engine discovery.
- **Sequence:**
  1. Designated human authority inspects staged snapshot and verifies data minimization.
  2. Authority records formal approval metadata (`ApprovedBy`, `ApprovedAt`).
  3. Snapshot transitions to `PUBLISHED_IMMUTABLE`. Content can never be modified in place.
  4. Portal presentation service serves the static snapshot from memory/static storage. Zero live SQL queries or transactional API routes exist between portal consumers and internal platform databases.
  5. Portal HTTP response headers strictly emit:
     ```http
     X-Robots-Tag: noindex, nofollow, noarchive
     Content-Security-Policy: default-src 'self'
     Cache-Control: private, no-cache, no-store
     ```
     Ensuring public fixtures remain completely shielded from external search engine indexing.

### 6.1 Explicit List of Prohibited and Redacted Attributes
The following attributes are strictly barred from appearing in any public contract or portal view:
1. **Internal Relational Identifiers:** Database autoincrement integer IDs, internal table names, foreign key references, and storage volume paths.
2. **Personal Identifiable Information (PII):** Real employee legal names, national identification numbers, personal email addresses, phone numbers, home addresses, or worker facial photos.
3. **Internal Security Attributes:** Password hashes, salt values, raw session tokens, session token digests, role definition bitmasks, and private permission assignments.
4. **Operational System Coordinates:** Database hostnames, port numbers, internal IP addresses, NATS cluster subject names, or internal microservice endpoints.
5. **Medical & Sensitive Findings:** Specific worker health notes, medical diagnoses, disability accommodations, or legal-privileged investigation correspondence.
