## 2. Threat Model and Reversible Abuse Cases

### 2.1 Methodology and Attacker Persona Profiles
The threat model employs the **STRIDE** methodology (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) evaluated against the 8 architectural trust boundaries (`TB-01` to `TB-08`) and the OSHE Inspect walking skeleton.

| Attacker Persona | Motivation / Capability | Attack Surface Targeted |
| :--- | :--- | :--- |
| **P-01: Untrusted Network Attacker** | External, unauthenticated. Scans for exposed ports, forged HTTP headers, and unauthenticated endpoints. | Ingress Gateway (`TB-02`), Local Identity Adapter (`TB-03`). |
| **P-02: Rogue / Malicious Tenant Member** | Authenticated within Tenant A. Attempts to access or tamper with Tenant B resources (IDOR, tenant header injection). | API Gateway (`TB-02`), Scoped Storage Adapter (`TB-05`), Audit Queries (`TB-04`). |
| **P-03: Compromised Safety Inspector** | Authenticated inspector attempting to fabricate inspection reports, modify closed safety findings, or delete non-compliant photos. | Workflow State Machine (`TB-04`), Evidence Upload (`TB-05`), Checklist Lifecycle (`TB-08`). |
| **P-04: Malicious Autonomous Sub-Agent** | Automated agent exceeding lease boundaries, altering governance records, or attempting unauthorized gate self-approval. | Agent OS Governance (`TB-01`), File Tree / Lease Control. |
| **P-05: Infrastructure / Edge Man-in-the-Middle** | Intercepts offline synchronization payloads, exploits race conditions or last-write-wins logic to mask severe safety hazards. | Site-Edge / Offline Boundary (`TB-08`), Outbox Dispatcher (`TB-06`). |

### 2.2 Reversible Abuse Cases (AC-01 through AC-07)

#### AC-01: Tenant Header Spoofing and Scope Escalation (Spoofing / Elevation)
- **Target Boundary:** `TB-02` (Client-to-Application Boundary).
- **Abuse Scenario:** Attacker authenticates as a low-privileged user in Tenant A, but sends forged HTTP request headers (e.g., `X-Tenant-ID: tenant_bravo_001` or `X-Company-ID: comp_safety_corp`) attempting to execute inspection actions or retrieve confidential safety findings belonging to Tenant B.
- **Vulnerability Vector:** Insecure Direct Object Reference (IDOR) or reliance on client-supplied tenancy headers.
- **Preventive Control:**
  1. Client-supplied tenancy headers are completely discarded at the API gateway.
  2. Server derives authoritative tenant context strictly from verified cryptographic claims via `MOD-IAM` and `MOD-ORG` (`DeriveTenantContext`).
  3. Any explicit client override attempt returns `ErrTenantOverrideForbidden` and immediately aborts the request.
- **Detective Control:** Audit logging in `MOD-REC` flags `ErrTenantOverrideForbidden` as a security tamper event with caller identity and origin IP.
- **Automated Verification:** `modules/organization-tenancy/tenant_context_test.go` (`TestDeriveTenantContext_OverrideDenial`, `TestAuthorizeTenantScope_CrossTenantDenial`).

#### AC-02: In-Place Mutation of Published Inspection Templates (Tampering)
- **Target Boundary:** `TB-04` (Inter-Module Encapsulation) & `TB-08` (Offline / Snapshot Boundary).
- **Abuse Scenario:** A tenant administrator or rogue user attempts to modify an approved, published safety checklist template in place (e.g., removing a mandatory fall-protection safety check) to disguise non-compliance after an incident occurs.
- **Vulnerability Vector:** Mutable template entity storage allowing in-place SQL `UPDATE` without version incrementation.
- **Preventive Control:**
  1. Template lifecycle in `MOD-CFG` enforces strict immutability once published (`PublishedMutationRejection`).
  2. Modifications produce an entirely new version (`v2.0.0`) in `DRAFT` status, retaining copy provenance.
  3. In-flight and completed inspections retain immutable snapshots of the exact checklist version referenced at instantiation (`InstantiateAndStaleVersionRetention`).
- **Detective Control:** Monotonic version check and audit trail in `MOD-REC` capturing all state transition attempts.
- **Automated Verification:** `modules/configuration-checklist/template_lifecycle_test.go` (`TestTemplateLifecycle_PublishedMutationRejection`, `TestTemplateLifecycle_InstantiateAndStaleVersionRetention`).

#### AC-03: Evidence Attachment Tampering and Digest Confusion (Tampering / Repudiation)
- **Target Boundary:** `TB-05` (Database vs. Object Storage Boundary).
- **Abuse Scenario:** Attacker uploads a modified or benign photo replacing an original inspection finding photo showing severe structural cracks, attempting to repudiate safety non-compliance before regulatory audits.
- **Vulnerability Vector:** Decoupled object storage writes without cryptographic checksum binding; overwritable object storage keys.
- **Preventive Control:**
  1. Cryptographic SHA-256 digest is computed on the byte stream during upload and bound to the PostgreSQL metadata record.
  2. Storage adapter (`MemoryStorageAdapter` / S3 client) verifies the stream digest matches the asserted digest prior to accepting the write; mismatches are rejected (`PutDigestMismatch`).
  3. Storage keys are immutable and prefixed with tenant namespace (`tenants/{tenant_id}/evidence/{file_id}`); overwrite of existing objects is architecturally forbidden.
- **Detective Control:** Periodic background integrity scan recomputes SHA-256 digests of stored objects and matches them against PostgreSQL audit metadata.
- **Automated Verification:** `modules/files-evidence/storage_adapter_test.go` (`TestMemoryStorageAdapter_PutDigestMismatch`, `TestMemoryStorageAdapter_CrossTenantIsolation`), `modules/records-audit/immutable_objects_test.go` (`TestVerifyIntegrityLinkage_TamperDigestFailure`).

#### AC-04: Cross-Tenant Data Leakage via Derived Projections (Information Disclosure)
- **Target Boundary:** `TB-07` (Derived Output Boundary).
- **Abuse Scenario:** Attacker submits crafted full-text search queries to Meilisearch or requests summary reports in `MOD-REP`, attempting to extract inspection findings, hazard notes, or inspector identities belonging to other tenants.
- **Vulnerability Vector:** Global / unpartitioned search index or reporting aggregation queries missing caller tenant filtering.
- **Preventive Controls:**
  1. Meilisearch documents and reporting queries are strictly partitioned by `tenant_id`.
  2. Report generation queries in `MOD-REP` enforce caller tenant scope at the API entry point (`TestCrossTenantDenial`).
  3. Search and report projections are formally designated **non-authoritative read models**; business rules and state machines never query derived models for authorization or state decisions.
- **Detective Controls:** Non-authority assertion in data access layer (`TestDerivedResultNonAuthority`).
- **Automated Verification:** `modules/reporting-localization/reporting_test.go` (`TestCrossTenantDenial`, `TestDerivedResultNonAuthority`, `TestAllowedFilterEnforcement`).

#### AC-05: Transactional Outbox Poisoning and Pipeline DoS (Denial of Service)
- **Target Boundary:** `TB-06` (Outbox and Asynchronous Message Boundary).
- **Abuse Scenario:** Attacker crafts malformed or oversized domain events that crash asynchronous event dispatchers or stall NATS JetStream consumers, halting critical corrective action notifications across the platform.
- **Vulnerability Vector:** Unvalidated event payloads, non-transactional staging, or lack of dead-letter isolation.
- **Preventive Controls:**
  1. Transactional Outbox pattern guarantees events are staged atomically within the same PostgreSQL ACID transaction as the business entity change (`TestOutbox_CommitPublication`, `TestOutbox_Rollback`).
  2. Schema and compatibility registry (`MOD-CTR`) validates event envelopes prior to staging.
  3. Dispatcher isolates repeatedly failing events into a poison quarantine queue (`TestPoisonEventQuarantine`), preventing head-of-line blocking.
  4. Consumers implement idempotent handling via monotonic event ID journaling (`TestDuplicateDispatch_Idempotency`).
- **Detective Controls:** Dispatch latency metrics and poison queue depth alerts.
- **Automated Verification:** `modules/events-outbox-jobs/event_outbox_test.go`, `modules/events-outbox-jobs/event_dispatcher_test.go`.

#### AC-06: Autonomous Agent Lease Escape and Gate Hijacking (Elevation of Privilege)
- **Target Boundary:** `TB-01` (Human and Agent Governance Boundary).
- **Abuse Scenario:** A compromised or misbehaving AI agent attempts to modify its own role profile, approve release gates, create public GitHub releases, or accept residual safety risks without human review.
- **Vulnerability Vector:** Delegated agent execution environments lacking strict role boundaries or automated gate validation.
- **Preventive Controls:**
  1. Leased execution governance (`ADR-0005`): Every agent operation requires an explicit, unexpired lease file with strict read/write path allowlists.
  2. Sole Human Owner invariant: Critical human decisions (`HDEC-*`) and gates (`H020-003`, `H020-007`, `HCOM-*`) strictly require non-delegable human approval.
  3. Pre-commit and CI hooks reject commits mutating governance policies without owner sign-off.
- **Detective Controls:** Automated repository scanners (`tools/validate_agent_os.py`, `tools/validate_repository.py`) and independent review leases (`IRL`).
- **Automated Verification:** `tests/test_permission_delegation.py`, `tests/test_validate_agent_os.py`.

#### AC-07: Blind Last-Write-Wins Masking Severe Safety Hazards (Tampering / Safety Hazard)
- **Target Boundary:** `TB-08` (Site-Edge / Offline Boundary).
- **Abuse Scenario:** Two field inspectors evaluate a construction site scaffold concurrently. Inspector A records a critical structural defect ("Scaffold at risk of imminent collapse — DO NOT USE"). Inspector B (operating on an offline device) submits a routine "OK" response 10 minutes later. A naive Last-Write-Wins (LWW) synchronization protocol overwrites the critical defect with "OK", leading to catastrophic workplace collapse.
- **Vulnerability Vector:** Blind LWW conflict resolution on safety-critical inspection states.
- **Preventive Controls:**
  1. Formal architectural prohibition of blind LWW for safety-critical states (`TST-V020-PLAN-001`).
  2. Inspection finding state machine in `MOD-WFA` requires explicit supervisor review before downgrade or closure (`TestReviewRejectionAndResubmission`).
  3. Synchronized findings maintain causal version tracking; conflicting submissions trigger explicit conflict flags and supervisor notifications.
- **Detective Controls:** Causal fork detection in synchronization journals; audit alerts for concurrent contradictory ratings.
- **Automated Verification:** `modules/workflow-action/business_rules_test.go` (`TestQualification_RollbackAndNonMutationOnDenial`), `modules/workflow-action/action_lifecycle_test.go` (`TestReviewRejectionAndResubmission`).

## 3. Privacy Impact Assessment (PIA) and Field-by-Field Review

### 3.1 Regulatory Context and Personal Data Protection Principles
The OSHE Platform processes occupational health, safety, and environmental inspection records. In accordance with the **Thailand Personal Data Protection Act B.E. 2562 (PDPA 2019)** and international data privacy baselines, the platform kernel enforces:
1. **Purpose Limitation:** Personal data is collected solely for workplace safety compliance, risk management, and regulatory recordkeeping.
2. **Data Minimization:** Only data strictly necessary for safety inspection evidence is collected; superfluous personal attributes are excluded.
3. **Storage Limitation & Erasure:** Immutable audit records and evidence files are governed by explicit retention tags and tenant-isolated cryptographic erasure mechanisms.
4. **Integrity and Confidentiality:** Cryptographic hashing, scoped storage isolation, and non-leaking diagnostic design.

### 3.3 Privacy Safeguards and Implementation Invariants

1. **Synthetic Engineering Data Invariant (`V020-D05`):** All v0.2.0 local development and internal alpha testing must execute exclusively on synthetic or redacted test fixtures. Committing or processing live customer PII, real national IDs, or actual medical records is strictly prohibited.
2. **Prohibited Data Classes:** The platform enforces automated scanner rules rejecting:
   - `CUSTOMER_DATA`: Live customer inspection records or actual tenant databases.
   - `MEDICAL_DATA`: Real worker health diagnostics, medical histories, or biometric templates.
   - `LEGAL_PRIVILEGED`: Attorney-client correspondence or litigation assessments.
3. **Non-Leaking Diagnostics (`NFR-V020-SEC-004`):** Error messages, panic handlers, and OpenTelemetry trace spans must sanitize sensitive attributes. Stack traces and database connection strings containing credentials or tokens are suppressed (`RedactedDiagnostics`). Verified by `localidentity_test.TestNegativeControl_NonLeakingDiagnostics`.
4. **Tenant-Isolated Erasure:** When a tenant lifecycle terminates or a retention window expires, evidence objects under `tenants/{tenant_id}/` and private database schema rows are purged via atomic tenant removal scripts without impacting neighboring tenants.

## 4. Product-Safety Hazard Log and Control Traceability

### 4.1 Safety Philosophy of the OSHE Platform
The OSHE platform governs life-safety, health, and environmental risk controls on physical industrial sites (construction, manufacturing, chemicals). A failure of software integrity in OSHE Inspect is not merely an IT defect—it can directly result in:
- Failure to halt work in an imminently dangerous environment (e.g., crane failure, trench collapse).
- Failure to alert site supervisors of unmitigated safety findings.
- Regulatory enforcement penalties, facility shutdowns, or criminal liability for workplace fatalities.

Therefore, safety hazards are governed by strict severity ratings and **fail-closed** engineering rules.

---

### 4.2 Severity Classification Framework

- **Severity 0 (`S0` — Critical Safety Blocker):**
  - False-negative safety evaluation (software reports "Safe" when a critical defect exists).
  - Silent dropping or unrecorded submission of high-risk safety findings.
  - Multi-tenant isolation failure exposing safety records or allowing cross-tenant state tampering.
  - Destruction or cryptographic corruption of incident evidence files.
  - *Release Effect:* **Absolute Release Blocker.** Zero tolerance. Requires immediate stop-work and root-cause analysis.
- **Severity 1 (`S1` — Major Safety Blocker):**
  - Stale checklist version hiding mandatory regulatory safety checks.
  - Transactional outbox failure delaying critical corrective action notifications beyond allowable window.
  - Inability to reconstruct append-only audit trail for regulatory inspection.
  - Database migration failure causing inconsistent state.
  - *Release Effect:* **Release Blocker.** Must be resolved before qualification unless formally excised by Sole Human Owner decision.
- **Severity 2 (`S2` — Major with Workaround):**
  - Derived search index lag where the UI explicitly alerts the user that search results are pending and directs them to authoritative database views.
  - *Release Effect:* Requires explicit Sole Human Owner waiver and remediation schedule.
- **Severity 3 (`S3` — Minor Defect):**
  - Non-misleading UI formatting discrepancies or localized string translation flaws.
  - *Release Effect:* Non-blocking for internal alpha; tracked in backlog.

## 5. Critical-Function Register

The platform kernel comprises nine critical functions that require fail-closed architectures, defensive validation, and deterministic qualification:

```
========================================================================================================================
Function ID | Function Name                 | Owning Module | Core Failure Impact                     | Fail-Closed Boundary
========================================================================================================================
CF-01       | Tenant Context Derivation      | MOD-ORG       | Multi-tenant cross-contamination        | Header override forbidden; unauthenticated deny
CF-02       | Access Policy Evaluation       | MOD-IAM       | Unauthorized privilege escalation       | Default-deny; real-time session revocation
CF-03       | Checklist Snapshot Invariant   | MOD-CFG       | Dynamic mutation of safety checks       | Immutable published templates; stale retention
CF-04       | Action State Machine           | MOD-WFA       | Premature or unverified hazard closure   | Role separation; rollback on rule failure
CF-05       | Cryptographic Evidence Hashing | MOD-EVD       | Evidence tampering / repudiation        | SHA-256 verification; immutable key prefixes
CF-06       | Append-Only Audit Journaling   | MOD-REC       | Audit trail loss or deletion            | Append-only monotonic store; no delete API
CF-07       | Transactional Outbox Staging   | MOD-EVT       | Notification loss / split-brain state   | ACID transaction binding; poison quarantine
CF-08       | Deterministic Report Rendering | MOD-REP       | Misleading safety compliance exports    | Non-authoritative models; source hash binding
CF-09       | Schema Migration Governance    | MOD-CTR       | Incompatible schema / data corruption   | Topological DAG migrations; M0-M2 verification
========================================================================================================================
```

### 5.1 Fail-Closed Posture Across Critical Functions
1. **Missing or Ambiguous Claims (`CF-01`, `CF-02`):** When authentication headers are missing, malformed, or ambiguous, the kernel halts execution immediately with an unauthenticated/unauthorized denial. No speculative guest or fallback tenant access is permitted.
2. **Business Rule Evaluation Failure (`CF-04`):** If a business rule qualification condition fails, the state transition is rejected and any pending database mutations are completely rolled back (`TestQualification_RollbackAndNonMutationOnDenial`).
3. **Digest Verification Mismatch (`CF-05`):** If a binary stream's SHA-256 hash does not match the asserted hash, the upload is terminated, the partial file is purged, and the metadata record is marked invalid.
