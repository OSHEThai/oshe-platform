## 2. Release Test Plan

### 2.1 Testing Philosophy and Deterministic Execution
The Milestone v0.3.0 test suite is engineered under the following core tenets:
1. **Hermetic Determinism:** Tests must execute without external network access, cloud provider credentials, or unseeded system entropy. Flaky or timing-dependent tests are classified as test failures.
2. **Injectable Time Control:** All temporal validations (session expiration, delegation validity windows, cache invalidation, and snapshot withdrawal) utilize an injected monotonic clock interface (`Clock`) allowing deterministic second-level time advancement.
3. **Synthetic-Only Data Exclusivity (`V020-D05`):** Test datasets and seeds comprise purely synthetic, fictionalized entities (e.g., `ten_alpha`, `usr_synth_01`). Committing or ingesting real employee identities, national IDs, or customer records is an immediate build-blocking violation.
4. **Fail-Closed Verification:** Safety-critical access control tests evaluate both positive granting paths and negative rejection behaviors. Rejection must result in generic, non-leaking diagnostic codes.

## 3. Assurance Plan and Verification Framework

### 3.1 Role Separation and Reviewer Independence
To maintain safety-critical governance standards, Milestone v0.3.0 enforces strict segregation of duties:
1. **Author Role Independence:** The author of any specification, code, or test fixture (e.g., Architecture Lead `w9:p22`, Security Lead `w9:p13`, or Engineering Lead) is strictly prohibited from performing the independent challenge review of their own work.
2. **Independent Review Role:** The **Test and Quality Lead / Independent Review and Challenge Agent (`w9:p14`)** executes an independent, single-pass challenge review of the exact candidate diff and test results.
3. **No Review Mutations:** The Independent Reviewer never modifies, stages, commits, or pushes candidate files. Any discrepancy results in a `NEEDS_CHANGES` or `FAIL` disposition returned to the PM Secretary (`w9:p21`).

### 3.2 Four-Stage Verification Gate Pipeline

```
[ Gate 0: Plan & Schema ] ──> [ Gate 1: Code & Contract ] ──> [ Gate 2: Test & Negative Controls ] ──> [ Gate 3: Pre-Merge Review ]
  - Issue deliverable check     - Clean modular boundaries       - 100% unit/integ test pass           - Single-pass challenge
  - Schema syntax valid         - Zero cross-module SQL          - 100% NFR benchmarks pass            - diff --check clean
  - validate_agent_os.py        - SHA-256 token hashing          - 100% Negative controls pass         - Traceability complete
```

### 3.3 Explicit Test Outcome Conventions
Every test execution and assurance review must report results using strict, unambiguous evaluation conventions. Reporting unknown, quarantined, or skipped checks as passing is strictly prohibited.

- **`PASS`**: The requirement, negative control, or benchmark was fully executed and met all acceptance criteria with zero assertion failures, zero unexpected warnings, and clean exit code `0`.
- **`FAIL`**: The test executed and failed to satisfy acceptance criteria, raised an unhandled exception, permitted an unauthorized action, leaked data across boundaries, or breached an NFR threshold.
- **`INCONCLUSIVE`**: The test could not execute to completion due to missing dependencies, timeout, environmental failure, or unseeded test fixtures. An inconclusive check blocks progression identically to a `FAIL`.

### 3.4 Evidence Integrity and Rerun Lineage
1. **Bit-Level Reproducibility:** Every evidence bundle must capture the exact git commit SHA, container image digest, toolchain version, and deterministic seed identifier.
2. **Cryptographic Sealing:** Raw test logs and execution outputs are hashed with SHA-256 and registered in the Evidence Manifest (`evidence-manifest.json`). Any post-execution modification invalidates the evidence record.

## 4. Migration, Rollback, and Archive Plan

### 4.1 Relational Schema Migration Strategy (`MOD-CTR`)
All database schema evolutions for Milestone v0.3.0 are governed through strict modular migration sequence controls:
1. **Topological Order Execution:** Migrations execute in dependency DAG order: `MOD-REC` $\rightarrow$ `MOD-ORG` $\rightarrow$ `MOD-IAM` $\rightarrow$ `MOD-CFG` $\rightarrow$ `MOD-WFA` $\rightarrow$ `MOD-EVD` $\rightarrow$ `MOD-REP` $\rightarrow$ `MOD-EVT`.
2. **Strict Schema Sovereignty:** Migrations for module `MOD-X` operate strictly within schema namespace `x` and table prefix `x_`. No migration may alter tables owned by another module.
3. **Idempotency and Atomic DDL:** Each migration file is transactional (`BEGIN ... COMMIT`). If any statement fails, the entire transaction rolls back cleanly without leaving orphaned tables or columns.
4. **Prohibition of Destructive DDL:** `DROP TABLE`, `DROP COLUMN`, or `TRUNCATE` statements are strictly barred from v0.3.0 migrations.

### 4.2 Rollback and Recovery Strategy
In the event of an unrecoverable failure during local alpha qualification:
1. **Downward Migration Scripts:** Each forward migration script (`V030_00X__*.up.sql`) is paired with an exact reverse migration script (`V030_00X__*.down.sql`).
2. **Clean Container Restoration:** Because v0.3.0 is a local alpha environment operating on synthetic fixtures, the baseline state can be fully restored within $\le 30$ seconds via:
   ```bash
   docker compose -f deploy/local/compose.dev.yaml down -v
   docker compose -f deploy/local/compose.dev.yaml up -d
   go run ./modules/ctr/cmd/migrate up --all
   go run ./modules/org/cmd/seed --fixture=fixtures/seeds/synthetic_baseline.json
   ```
3. **Rollback Trigger Conditions:**
   - Any failure of `validate_agent_os.py` or database migration integrity.
   - Any cross-tenant isolation breach detected during test execution.
   - Accidental injection of live customer data or plaintext credentials.

### 4.3 Historical Attribution and Archival Plan (`H030-002`)
1. **Zero Hard Deletion Rule:** In compliance with safety regulatory requirements, operational records, user accounts, and contractor associations are never physically deleted from persistence stores (`DELETE FROM ...` is blocked).
2. **Soft-Delete Lifecycle:** Entity removal triggers a transition to `StateArchived` (`ARCHIVED`):
   - Sets `is_archived = TRUE` and `archived_at = CURRENT_TIMESTAMP`.
   - Records acting subject ID and reason code.
   - Emits `entity.archived` event to append-only audit journal (`rec_audit_journal`).
3. **Archived Sub-Tree Freezing:** Downstream child entities under an archived parent (e.g., Areas under an archived Site) are immediately frozen and reject operational updates or new child attachments (`ErrParentArchived`).
4. **Audit Immutability:** The audit journal in `MOD-REC` is append-only. Truncation or updating of audit rows is prevented by database-level triggers.

## 5. Revocation and Withdrawal Plan

Milestone v0.3.0 establishes explicit, deterministically verified procedures for session termination, delegation expiration, contractor removal, and public portal snapshot withdrawal:

```
+----------------------------------------------------------------------------------------------------+
|                                    REVOCATION & WITHDRAWAL PATHWAYS                                |
+-----------------------+------------------------+-------------------------+-------------------------+
| Target Domain         | Revocation Trigger     | Mechanism & Latency     | Fail-Closed Outcome     |
+-----------------------+------------------------+-------------------------+-------------------------+
| Bearer Session Tokens | Logout / Security Term | Revocation Registry     | Invalidation $\le 50$ ms|
| (iam_sessions)        | / Inactivity Timeout   | (Valkey token hash map) | Subsequent calls HTTP 401|
+-----------------------+------------------------+-------------------------+-------------------------+
| Time-Bounded          | Delegator Revocation / | Invalidate record in    | Immediate denial on     |
| Delegations           | Clock Exceeds valid_to | MOD-IAM / temporal gate | next evaluation (403)   |
+-----------------------+------------------------+-------------------------+-------------------------+
| Sponsored Contractor  | Sponsor Termination /  | Set StateArchived in    | Token validation fails  |
| Parties (prt_*)       | Sponsorship Expiration | MOD-ORG contractor link | with HTTP 401 closed    |
+-----------------------+------------------------+-------------------------+-------------------------+
| Portal Snapshots      | Data Error / Finding   | Set StateWithdrawn in   | Portal serves HTTP 410  |
| (rep_snapshots)       | Dispute / Lead Retract | MOD-REP snapshot store  | Gone with audit notice  |
+-----------------------+------------------------+-------------------------+-------------------------+
```

### 5.1 Real-Time Identity and Session Revocation (`NFR-V030-REV-001`)
- **Revocation Trigger:** Explicit user logout, administrative session termination, or idle timeout ($\ge 15$ minutes).
- **Execution Mechanism:** Gateway writes token digest to `MOD-IAM` revocation registry and evicts session from Valkey memory cache.
- **Latency Requirement:** Invalidation takes effect system-wide within $\le 50$ ms.
- **Verification Harness:** Test `test_immediate_session_revocation` issues an active session token, executes an authorized call, triggers revocation, and asserts the subsequent call within 50 ms fails closed with HTTP 401 Unauthorized.

### 5.2 Time-Bounded Delegation Expiration and Revocation (`H030-003`)
- **Revocation Trigger:** Delegating manager manually revokes delegation grant, delegator leaves company / transitions to `ARCHIVED`, or clock advances beyond `valid_to`.
- **Execution Mechanism:** Policy evaluator checks delegation record validity against injected `Clock`. If current time $> \text{valid\_to}$, or delegator is inactive, delegation is treated as null.
- **Verification Harness:** Test `test_delegation_temporal_expiry` advances mock clock by 1 second past `valid_to` and verifies access is immediately denied with `DenialReasonDelegationExpired` (HTTP 403).

### 5.3 Sponsored Contractor Expiration and Fail-Closed Posture (`H030-004`)
- **Revocation Trigger:** Contractor agreement terminates, internal sponsor departs, or expiration timestamp arrives without manual renewal.
- **Execution Mechanism:** `MOD-ORG` updates contractor party record to `ARCHIVED`. Session validation pipeline checks sponsor active status and contractor expiration on every authenticated request.
- **Fail-Closed Rule:** Expired contractor accounts fail closed immediately (`DenialReasonIdentityInactive`). Automatic perpetuation or grace periods are strictly prohibited.

### 5.4 Portal Snapshot Withdrawal Procedure (`NFR-V030-REC-001`)
- **Withdrawal Trigger:** An authorized compliance lead discovers an erroneous finding or revokes approval for an inspection report.
- **Execution Procedure:**
  1. Compliance lead issues snapshot retraction command: `WithdrawSnapshot(snapshot_id, reason_code)`.
  2. Snapshot state in `MOD-REP` transitions from `PUBLISHED_IMMUTABLE` to `WITHDRAWN`.
  3. Presentation payload is purged from static serving cache; an immutable tombstone record is staged.
  4. An append-only audit event (`snapshot.withdrawn`) is recorded in `MOD-REC`.
  5. Subsequent portal requests for the snapshot URL immediately return HTTP 410 Gone with a non-authority notice.
- **Latency Benchmark:** State transition and cache invalidation execute within $\le 1$ second (surpassing the $\le 5$ minute alpha ceiling).
