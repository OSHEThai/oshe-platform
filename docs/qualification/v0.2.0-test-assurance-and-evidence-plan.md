## 2. Test Basis and Design Driver

In accordance with `V020-D01` and `V020-D04`, the primary design driver for v0.2.0 test qualification is the **OSHE Inspect walking skeleton** operating across the modular monolith baseline:

1.  **Modular Monolith Boundaries (`V020-D04`):** Modules own their respective data stores and domain logic. Direct cross-module database writes and private table joins are strictly prohibited; inter-module interactions must proceed exclusively through versioned public Go contracts or transactional outbox events.
2.  **Supported Profile Immutability (`V020-D02`, `V020-D03`):** Testing must be executed against the single frozen local development / internal-alpha runtime profile:
    *   **Backend:** Go 1.26.5 (`net/http`, chi 5.3.2, pgx 5.10.0, goose 3.27.3, OpenTelemetry Go 1.46.0).
    *   **Frontend:** React 19.2.8, TypeScript 7.0.2, Vite 8.2.2, Tailwind CSS 4.3.3, TanStack Query 5.102.8, i18next 26.4.1.
    *   **Local Services (Containerized with SHA-256 image digests):** PostgreSQL 17.11 (with optional PostGIS 3.6.4), Meilisearch 1.51.0, Valkey 9.1.1, SeaweedFS 4.29 (S3 API compatibility), and NATS JetStream 2.14.5.
    *   **Validation Tooling:** Python 3.14.7, Node.js 24.20.0 LTS, pnpm 11.24.0, Docker Engine 29.7.2, Compose 5.4.0.
3.  **Local-Only and Adapter-First Integration (`V020-D11`, `V020-D12`):** Tests must operate strictly with local mocks, adapters, and emulators. External identity providers, external notification services, and paid provider routes are prohibited.

## 4. Walking-Skeleton Scenarios (WS-01 – WS-08)

The v0.2.0 walking skeleton comprises eight end-to-end integration scenarios representing the core lifecycle of OSHE Inspect:

*   **WS-01 (Context & Identity):** Establish tenant, organization, project, and site context; authenticate via local identity adapter/emulator; resolve membership permissions; verify immediate denial of unauthorized users outside defined tenant scope.
*   **WS-02 (Configuration & Versioning):** Create a draft checklist/inspection template, submit for review, publish an immutable versioned definition, and confirm subsequent edits produce a new version without mutating historical versions.
*   **WS-03 (Execution & Record Declaration):** Instantiate an inspection execution from a published checklist version, collect responses, validate field constraints, execute authorized state transitions, and declare an immutable completed record.
*   **WS-04 (Evidence Attachment):** Upload an original image/document to SeaweedFS (S3 API), verify SHA-256 content digest, link artifact to inspection record, generate derivative previews independently, enforce tenant-scoped access, and verify export completeness.
*   **WS-05 (Finding & Corrective Action):** Log a safety finding from inspection responses, assign a corrective action to a responsible role, record remedial evidence, execute state transitions (open $\rightarrow$ in-progress $\rightarrow$ resolved), and require authorized verification before closure.
*   **WS-06 (Transactional Outbox & Events):** Ensure business record mutation and outbox event persistence occur within a single ACID transaction; dispatch event to NATS JetStream; verify correct deduplication and idempotent handling on consumer replay.
*   **WS-07 (Reporting & Export):** Render a deterministic inspection summary report incorporating definition version, recorded timestamps, limitations, and cryptographic file digests; ensure export package includes complete audit history.
*   **WS-08 (Migration & Recovery):** Execute forward database migrations on a fresh instance, verify rollback/forward-fix procedures under simulated failure, perform a complete backup/restore cycle, and verify data integrity via cryptographic checksums.

## 5. Test-Data Limits and Data Classification

In strict compliance with `V020-D05` and `repo-manifest.yaml`, the execution of all tests must adhere to rigorous data boundaries:

1.  **Permitted Data:** Only **synthetic, mocked, or explicitly approved low-risk engineering data** may be introduced into test fixtures, mock servers, or local databases.
2.  **Strictly Prohibited Data Classes:**
    *   `CUSTOMER_DATA`: Live customer names, identifiers, credentials, or actual operational inspection data.
    *   `PRODUCTION_DATA`: Any dump, clone, or subset of production database state.
    *   `PRODUCTION_SECRETS`: Production API tokens, signing keys, private certificates, or production passwords.
    *   `MEDICAL_DATA`: Real occupational health diagnoses, clinical measurements, or medical records.
    *   `SECURITY_CASE_DATA`: Live incident notes, threat intelligence investigations, or vulnerability reports.
    *   `LEGAL_PRIVILEGED`: Attorney-client correspondence or privileged legal assessments.
3.  **Secret Exclusion Rule (`NFR-V020-SEC-002`):** Automated pre-commit and CI scans (`tools/validate_repository.py`) must scan all test fixtures, mock data, and test reports to ensure zero credentials or tokens are committed.

## 6. Evidence Contract and Minimum Result Fields

To satisfy `.ai/policies/evidence.yaml` and `.ai/schemas/evidence-record.schema.json`, every recorded test outcome must capture the following standardized metadata:

*   `evidence_id`: Unique identifier conforming to `^EVD-V020-[A-Z0-9-]+$`.
*   `evidence_class`: Standardized classification (`STATIC`, `CONTRACT`, `SYNTHETIC`, `CI`, `RUNTIME`, `INDEPENDENT_REVIEW`, or `HUMAN`).
*   `claim`: Exact, unambiguous technical claim being verified.
*   `repository`: Target repository (`OSHEThai/oshe-platform`).
*   `commit`: Full 40-character git commit SHA of the exact tested code tree.
*   `environment`: Supported profile identifier (e.g., `local-supported-profile-v020`).
*   `command_or_method`: Exact reproducible command executed (e.g., `go test -v ./...` or `python tools/run_local_ci.py`).
*   `result`: Explicit result status (`PASS`, `FAIL`, `SKIPPED`, `INCONCLUSIVE`, `QUARANTINED`). *Note: Skipped, inconclusive, or quarantined results never satisfy a passing gate.*
*   `artifact_refs`: Relative paths to test logs, coverage files, and SHA-256 digest manifests.
*   `captured_at`: ISO-8601 UTC timestamp of execution.
*   `captured_by`: Authenticated agent or engineer identity.
*   `limitations`: Explicit itemization of test boundaries, excluded environments, and known non-functional constraints.
*   `review_ref`: Pointer to corresponding independent review lease or finding.
*   `human_decision_ref`: Pointer to owner authorization decision (e.g., `HDEC-V020-GATE-B-APPROVAL-051`).

## 7. Defect Severity and Release-Blocking Rules

Defects identified during test execution are categorized according to the project severity taxonomy, each imposing strict release gating rules:

*   **Severity 0 (`S0` — Critical Blocker):**
    *   *Conditions:* Multi-tenant isolation failure / cross-tenant data leak; unauthorized bypass of protected state transitions; unrecoverable loss of committed inspection records; corruption of original evidence files; discovery of live credentials/secrets; or misleading safety-critical status.
    *   *Rule:* **Absolute Release Blocker.** Zero tolerance. Requires immediate halt of the release line and root-cause analysis.
*   **Severity 1 (`S1` — Major Blocker):**
    *   *Conditions:* Failure of any walking-skeleton scenario (WS-01 through WS-08); repeatable database migration or restore failure; broken audit trail reconstruction; or absence of an approved fallback mechanism.
    *   *Rule:* **Release Blocker.** Must be resolved before qualification unless the affected capability is formally excised from release scope by an owner decision.
*   **Severity 2 (`S2` — Major with Workaround):**
    *   *Conditions:* Significant non-conformance with a documented, tested, and non-security-weakening workaround.
    *   *Rule:* Requires explicit Sole Human Owner waiver, documented operational tracking, and a scheduled remediation issue.
*   **Severity 3 (`S3` — Minor Defect):**
    *   *Conditions:* Superficial UI inconsistencies, non-misleading formatting flaws, or minor telemetry discrepancies.
    *   *Rule:* Non-blocking for internal alpha; entered into the defect backlog.
*   **Process Blockers:** Missing evidence records, unverified environments, missing restore tests, or incomplete independent reviews automatically fail the qualification gate regardless of software test scores.

## 8. Non-Functional Requirements (NFR) Internal Target Treatment

In accordance with `V020-D06` and the v0.2.0 Non-Functional Requirements Catalog (`NFR-V020-001`), performance and recovery metrics are defined strictly as **internal engineering targets**:

| Metric ID | Parameter | Internal Engineering Target | Treatment and Limitation Boundary |
|---|---|---|---|
| `NFR-V020-PERF-001` | Common API Latency | p95 $\le$ 750 ms | Internal development guideline under frozen local alpha load. **Never a public SLA or service commitment.** |
| `NFR-V020-UX-001` | UI Usability | Usable $\le$ 2.5 s | Target for initial render on minimum supported device with local assets cached. **Not an external commitment.** |
| `NFR-V020-REC-001` | Environment Restore | $\le$ 8 hours | Internal disaster recovery drill objective following accepted loss decision. |
| `NFR-V020-REC-001` | Transient-State Loss | $\le$ 24 hours | Maximum tolerated recovery point for uncommitted transient state during alpha. |
| `NFR-V020-OFF-002` | Offline Reference Data | Freshness $\le$ 24 hours | Internal cache validity target for non-critical inspection templates. |

**Quality Claim Invariant:**
No performance, availability, reliability, or scalability claims may be published or asserted externally based on local test runs. Internal engineering alpha software is explicitly classified as non-production, non-high-availability software.

## 9. Gate and Acceptance Criteria

### 9.1 Execution Entry Criteria
Before any test execution may be submitted for milestone credit:
1.  Target codebase is committed and clean on the approved branch.
2.  Supported local profile versions and OCI image digests are locked and verified.
3.  Synthetic test data fixtures are reviewed and confirmed free of prohibited data.
4.  Local database migration and clean-slate seed scripts are verified.

### 9.2 Release Exit Criteria
Milestone completion and release qualification require:
1.  Execution of all mandatory suites with zero unresolved S0 or S1 defects.
2.  Complete pass of the walking skeleton scenarios (WS-01 through WS-08).
3.  100% pass on negative authorization and tenant isolation abuse test suites.
4.  Verified database backup and successful full restore drill.
5.  All test evidence captured in immutable, schema-compliant evidence records.
6.  Independent Review and Challenge Lead recorded `PASS` disposition.
7.  Sole Human Owner formal acceptance under a dedicated release decision.
